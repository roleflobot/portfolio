# 미니프로젝트 1 — 고객 VOC 분석 Agent

## 제출 링크

- **Google Form (제출용)**: https://docs.google.com/forms/d/e/1FAIpQLSf-hHlZoB6HqiLrQeLZn9sL-UvxZXN0-hJmQgCdrlm6TbJYEQ/viewform
- **Google Sheet (원마켓 고객 문의 접수)**: https://docs.google.com/spreadsheets/d/11RuxFazaelzIocwhrHea9544uZWWA57G8BFuByvuTQ0/edit?resourcekey=&gid=566082185#gid=566082185
  - `응답` 탭: Google Form 원본 응답이 자동 누적되는 곳
  - `분석 결과` 탭: n8n이 분석·저장한 최종 결과 (위 링크가 바로 이 탭으로 열림)

## 전체 흐름

```
고객 → Google Form 제출 → Google Sheet(응답 탭)에 자동 추가
   → n8n이 새 행 감지
   → 아이템 1개씩 순차 처리(03_Loop_Over_Items)
   → 중복 조회 → 중복이면 즉시 정상 종료(저장/알림 없음)
   → 신규 건이면 Gemini로 5개 필드 구조화 분류
   → 출력값 검증·안전 보정
   → 분석 결과 시트에 저장
   → urgency=상인 건만 Discord 채널로 즉시 알림
```

## n8n 워크플로우 노드 구성 (`Project 1 VOC`, Published)

| 노드 | 역할 |
|---|---|
| `02_Google_Sheets_Trigger` | `응답` 탭에 새 행이 추가되면 자동 실행 (rowAdded, 1분 폴링) |
| `02_Normalize_Input` | 한글 열 이름 → 표준 필드명 변환, 물품번호+정규화된 문의내용으로 `dedupe_key` 생성 |
| `03_Loop_Over_Items` | 폴링이 신규 행을 여러 개 동시에 감지해도 아이템을 1개씩 순차 처리하도록 강제 (다중 아이템 유실 버그 방지) |
| `03_Search_Analysis_Sheet` | `분석 결과` 탭에서 `dedupe_key`로 기존 처리 이력 조회 |
| `04_Is_Duplicate` | 조회 결과 존재 여부로 중복 판정 |
| `05_Stop_Duplicate` | 중복이면 저장·알림 없이 정상 종료 (LLM 호출 전 차단) |
| `06_LLM_Classify` | Gemini `generateContent` 직접 호출. `responseSchema`로 category/sentiment/urgency/summary/needs_review 5개 필드 구조화 출력 강제 |
| `07_Parse_Validate_JSON` | LLM 응답 파싱·계약 검증(허용값/타입/summary 길이). 위반 시 `urgency=중`, `needs_review=true`로 안전 보정하되 반드시 저장 진행 |
| `08_Generate_Ticket_Metadata` | 접수번호(`VOC-YYYYMMDD-실행ID`), 처리시각, Discord용 200자 말줄임 원문 생성 |
| `09_Save_Analysis_Result` | `분석 결과` 탭에 15개 열 append (검증 실패건 포함, 전량 저장) |
| `10_Is_Urgency_High` | `urgency === '상'` 여부 분기 |
| `11_Send_Discord_Webhook` | 상인 건만 Discord Webhook으로 즉시 알림 |
| `12_End_Normal` | 중/하 건 정상 종료 (알림 없음) |

## 요구사항 충족 내역

- **REQ-01 수집**: Google Form 4개 필수 항목(문의유형/문의내용/이메일/물품 번호) 그대로 사용, Sheet에 자동 누적
- **REQ-02 트리거**: Google Sheets Trigger로 신규 행 자동 감지·실행 (수동 실행 아님, Published 상태로 운영)
- **REQ-03 중복 방지**: `dedupe_key`(물품번호+정규화된 문의내용) 조합으로 LLM 호출 이전에 차단. 실제 운영 중 동일 문의 재제출 테스트에서 분석 결과에 행이 추가되지 않음을 확인
- **REQ-04 LLM 분류**: Gemini에 `responseSchema`로 5개 필드+허용값을 강제. 긴급도 판정 기준(상/중/하)을 시스템 프롬프트에 명시
- **REQ-05 검증 안전판**: 필수 필드 누락/허용값 위반/타입 불일치를 코드로 검사, 위반 시 `urgency=중·needs_review=true`로 보정하고 검증 실패건도 반드시 시트에 저장
- **REQ-06 결과 저장**: 모든 비중복 건(검증 실패 포함)을 `분석 결과` 탭에 기록
- **REQ-07 Discord 긴급 알림**: `urgency=상`인 건만 Webhook으로 발송, 메시지에 접수번호/분류/요약/원문(200자 말줄임)/접수시각 5가지 포함. 중·하 건은 전송하지 않음(실제 운영 로그로 확인)

## 실제 운영 검증

Publish 후 실제 Google Form 제출로 파이프라인을 검증했습니다.

- 실제 문의 다수 건이 문의 내용에 따라 각기 다른 category/sentiment/urgency로 정확히 분류되어 저장됨
- urgency=상 건들이 Discord 채널로 실시간 발송됨(접수번호/분류/요약/원문/접수시각 5요소 정상 표시)
- 동일 물품번호+동일 문의내용으로 재제출한 테스트 건은 분석 결과 시트에 중복 행 없이 정상 차단됨

## REQ-05 검증 안전판 — Pin Data 기반 계약 위반 테스트

Gemini에 `responseSchema`(구조화 출력)를 걸어두면 모델이 스스로 계약을 어기는 경우가 실제로는 거의 발생하지 않습니다. 그래서 REQ-05("LLM 출력이 계약을 어겨도 워크플로우가 죽으면 안 됨")를 제대로 검증하려면 실제 Gemini 호출과 무관하게, `07_Parse_Validate_JSON` 앞에 **가짜 LLM 응답을 직접 주입**해서 계약 위반 상황을 인위적으로 재현해야 했습니다. n8n의 Pin Data 기능으로 운영 프롬프트·credential은 전혀 건드리지 않고 다음 4가지 위반 유형을 각각 독립적으로 테스트했습니다.

| 위반 유형 | 주입한 가짜 응답 | 결과 |
|---|---|---|
| 필수 필드 누락 | `urgency` 필드 자체가 없는 JSON | `INVALID_URGENCY` 기록, urgency=중·needs_review=true로 보정 후 저장 |
| 허용값 위반 | category/sentiment/urgency 전부 허용값 밖의 값 | 3개 오류 모두 기록, 동일하게 안전 보정 후 저장 |
| 타입 불일치 | `needs_review`가 boolean이 아닌 문자열 `"false"` | `INVALID_NEEDS_REVIEW` 기록, 안전 보정 후 저장 |
| JSON이 아닌 응답 | 순수 자연어 문장 | JSON 파싱 실패 포함 6개 오류 기록, 안전 보정 후 저장 |

4가지 경우 모두 워크플로우가 중단되지 않고(`status: success`), `urgency=중·needs_review=true`로 안전하게 보정된 채 분석 결과 시트에 정상 저장되었으며, urgency가 상이 아니므로 Discord 알림은 발송되지 않았습니다(검증 실패건도 시트에는 반드시 남아야 한다는 요구사항 충족). `validation_error` 열에는 매번 구체적인 실패 사유가 정확히 기록됨을 확인했습니다.

## 개발 중 겪은 문제와 해결 — 다중 아이템 동시 유입 시 데이터 유실 버그

### 발견 경위

폴링 주기(1분) 안에 신규 문의가 2건 이상 동시에 들어오는 상황을 테스트하다가, 트리거가 한 번에 감지한 여러 아이템 중 **첫 번째를 제외한 나머지가 파이프라인에서 통째로 사라지는** 현상을 발견했습니다. 실행 로그를 직접 열어보니 원인은 다음과 같았습니다.

- `03_Search_Analysis_Sheet`(Google Sheets "Get row(s)")는 여러 입력 아이템을 받아도 **아이템별로 따로 실행되지 않고 딱 한 번만 실행**됩니다.
- 이때 조회 필터(`{{ $json.dedupe_key }}`)는 **첫 번째 아이템의 값으로만** 평가되어, 그 값으로 Google Sheets API 조회가 단 한 번 나갑니다.
- 나머지 아이템들은 조회 대상에 아예 포함되지 못하고 그 시점에 사라지며, 이후 `04_Is_Duplicate`~`11_Send_Discord_Webhook`의 어떤 노드에도 도달하지 못합니다.
- 트리거는 이미 그 행들을 "처리한 행"으로 표시하므로 다음 폴링에서도 재시도되지 않아 **영구 유실**됩니다.
- 실행 상태는 `status: success`로 표시되어, 로그만으로는 데이터가 유실됐다는 사실을 전혀 알 수 없습니다. 만약 유실된 문의 중 하나가 urgency=상 건이었다면, 분류·저장·Discord 알림 없이 조용히 누락됩니다.

### 해결

`02_Normalize_Input`과 `03_Search_Analysis_Sheet` 사이에 **`03_Loop_Over_Items`(Split in Batches, batchSize=1)**를 추가했습니다. 트리거가 신규 행을 몇 건 동시에 감지하든, 이 노드가 아이템을 1개씩 끊어서 `03` 이후 체인에 넘기고, 각 아이템이 중복 판정(`05_Stop_Duplicate`)이나 정상 처리(`11_Send_Discord_Webhook`/`12_End_Normal`)로 끝나면 다시 `03_Loop_Over_Items`로 되돌아가 다음 아이템을 이어 처리하도록 구성했습니다.

### 검증

동일 폴링 주기에 2건(일반 문의 1건 + 중복 결제·환불 요구 urgency=상 1건)이 동시에 감지되는 상황을 재현해, 수정 전에는 두 번째 건이 완전히 사라지던 것이 수정 후에는 두 건 모두 각각 독립적으로 끝까지 처리(분류→저장→urgency 분기)되는 것을 실행 로그로 확인했습니다. 이후 실제 운영(Publish 상태)에서도 다건 제출 테스트로 재확인했습니다.
